# AGENTS.md

## Контекст проекта

- Учебный frontend-проект для современных практик разработки.
- Главная цель пользователя — поддерживаемая, предсказуемая и масштабируемая кодовая база без преждевременного усложнения.
- Стек: React 19, TypeScript 7, Vite 8, Zustand 5, GTK Adwaita для React (`@gtk-js/adwaita`). React Router не установлен: добавлять только вместе с реальной маршрутизацией.
- Проект небольшой: основной пример — список задач через Zustand. Не переносить шаблонные или крупные архитектурные решения без реальной необходимости.
- Основной язык общения с пользователем — русский.

## Текущее состояние

- `src/main.tsx` — точка входа, рендер приложения в `StrictMode`.
- `src/app/App.tsx` — корневой компонент и композиция страниц.
- `src/app/App.tsx` также содержит `AdwaitaProvider`, прозрачную шапку (`AdwHeaderBar` с классом `flat` и `ThemeSwitcher`, обычный блок в потоке страницы) и подключает `TodoPage`.
- `src/todo/` — модуль задач без слоёв:
  - `todoStore.ts`: тип `Todo`, store `useTodoList` (Zustand persist в `localStorage`, ключ `todo-list`, сохраняются только `todoList`; при загрузке принимаются только корректные задачи) и действия `addTodo`, `toggleTodo`, `editTodo`, `deleteTodo`, `clearCompletedTodos`, `undoDelete`. `addTodo` и `editTodo` обрезают заголовок и отбрасывают пустой, `addTodo` кладёт новую задачу в начало. `deletedTodos` (задача, индекс и предыдущая задача) хранит последнее удаление для отмены и не сохраняется.
  - `TodoPage.tsx`: композиция, уведомления об удалении с отменой (`AdwToastOverlay`), живая область `role="status"`, глобальные клавиши вне полей ввода (**Ctrl+Z** отмена, **Shift+Delete** очистка завершённых; **Ctrl+Shift+Delete** не использовать: его перехватывает браузер). Вся страница скроллится, закреплённая полоса (`position: sticky; top: 0`) содержит панель действий и строку новой задачи, под ней зона 24px с градиентом, `backdrop-filter: blur` и маской. Не оборачивать страницу в `AdwToolbarView` и другие контейнеры с `overflow`, иначе sticky перестанет работать относительно окна.
  - `NewTodoRow.tsx`: строка новой задачи (`AdwEntryRow` с названием «Новая задача» вместо placeholder, без подсказок про клавиши). Enter создаёт, Esc очищает, **↓** переходит к списку; на `hasTouch` внутри строки показываются «Отмена» и «Подтвердить» (`RowActions.tsx`).
  - `TodoList.tsx`: список с roving tabindex (одна Tab-остановка, `activeId` обновляется по фокусу) и клавишами на самой строке (стрелки, Home, End, Пробел, Enter и F2, Delete и Backspace). Обработчик нативный на этапе capture с `stopPropagation`, потому что `AdwPreferencesGroup` сам двигает фокус стрелками и на краях уводит его, как Tab. Фокус после удаления идёт на соседнюю строку или в строку ввода, после редактирования возвращается на строку.
  - `TodoItem.tsx` (строка просмотра без чекбокса: состояние «выполнено» передаётся зачёркнутым названием и именем строки `aria-label="<название>, выполнено"`. Статус меняют кнопка «Отметить как сделанное» или «Вернуть в работу» рядом с карандашом или урной (только если есть мышь, `hasMouse`), горизонтальный свайп любым пальцем или пером (`shared/useHorizontalSwipe`, мышью не работает) и Пробел на строке. Кнопки внутри строки с `tabIndex={-1}`, на устройствах с `hover: hover` они видны только при наведении или клавиатурном фокусе на строке или внутри неё, правило в `TodoItem.module.css`, там же `touch-action: pan-y`) и `TodoItemEditor.tsx` (редактирование на месте через `AdwEntryRow`; `AdwEntryRow` переносит строку в DOM списка уже после монтирования, поэтому фокус ставится на следующем кадре, и только после него включается сохранение по потере фокуса).
  - Свайп смещает строку за пальцем, поэтому `TodoList.module.css` обрезает горизонтальное переполнение (`overflow-x: clip`): иначе мобильный браузер расширяет раскладку и уменьшает масштаб страницы. Свайп как единственный способ на касаниях не даёт альтернативы для скринридеров (WCAG 2.5.1): сейчас альтернатива — пробел и пометка в имени строки (см. issue #6).
  - `TodoToolbar.tsx` и `ClearCompletedButton.tsx`: панель иконок (сейчас одна иконка очистки завершённых). `placement="top"` (есть мышь) — над строкой ввода, высота 34px зарезервирована всегда, поэтому появление кнопки не сдвигает интерфейс. `placement="bottom"` (устройство только с касаниями, `hasTouch && !hasMouse`) — закреплена внизу окна, ближе к большому пальцу, поверх страницы; у контента снизу запас, у `AdwToastOverlay` смещение 58px. Выбор места делает `TodoPage`.
  - `ShortcutHints.tsx`: закреплённая внизу окна полоса (`role="note"`) с подсказками по клавишам, действующим сейчас. Контекст фокуса определяется по DOM (`data-new-todo`, `data-todo-editor`, `data-todo-id`) через `useSyncExternalStore` на `focusin`/`focusout`. В полях ввода не предлагаются `?`, `Ctrl+Z` и `Shift+Delete` (они принадлежат полю), на устройствах только с касаниями полоса скрыта, как и кнопка справки в шапке (клавиша **?** и сами горячие клавиши работают). У контента страницы снизу запас под полосу, у `AdwToastOverlay` смещение 40px. При добавлении клавиши обновлять её здесь, в `ShortcutsHelp.tsx`, README и тестах.
  - `ShortcutsHelp.tsx`: кнопка в шапке и диалог со списком горячих клавиш; открывается и клавишей **?**. При добавлении клавиши обновлять список в этом файле, `README.md` и в тестах.
- Добавление, удаление и «Удалить завершённые» выполняются через `shared/withViewTransition` (View Transitions API: `document.startViewTransition` + `flushSync`); строки `TodoItem` имеют `view-transition-name: todo-<id>`, список — `todo-list`, правила View Transition лежат в `shared/withViewTransition.css`. Без поддержки API и при `prefers-reduced-motion` обновление применяется сразу. Не оборачивать в transition частые обновления (набор текста, toggle): применение состояния откладывается на кадр, и чекбокс на мгновение остаётся в старом положении. `withViewTransition(update, onApplied)`: `onApplied` вызывается после применения в DOM (например, вернуть потерянный фокус). В тестах после действия, которое идёт через transition, нужно дождаться результата (например, появления чекбокса), прежде чем нажимать следующую клавишу.
- `src/shared/` — `useMediaQuery` (подписка на `matchMedia` через `useSyncExternalStore`) и `useDeviceInfo` → `{ isMobile (pointer: coarse — тип устройства, не зависит от ширины, поэтому раскладной смартфон остаётся мобильным и в развёрнутом виде), isCompact (≤600px), hasTouch (any-pointer: coarse), hasMouse (any-pointer: fine + any-hover: hover), isFoldSpanned (окно разделено сгибом) }`. `App` пишет их в `html[data-mobile|compact|touch|mouse|fold-spanned]`; при `hasTouch` отмена и подтверждение ввода вместо Esc/Enter доступны кнопками внутри строки (`RowActions`). Правило `@media (horizontal-viewport-segments: 2)` в `index.css` держит контент в первой половине экрана; оно не покрыто тестами (Chromium в Playwright не эмулирует сгиб). Определять устройство только через `useDeviceInfo`, не по user agent.
- Стили и тема приходят из `@gtk-js/adwaita` (`AdwaitaProvider` в `App`); Ant Design и Panda CSS удалены. Собственные стили: `src/index.css` — слой `reset` (только сброс браузерных значений) и слой `base` (глобальные стили приложения: `scrollbar-gutter: stable` против сдвига вёрстки при появлении скролла, фон и цвет `body` из `--window-bg-color` / `--window-fg-color` Adwaita, корневой контейнер, раскладные экраны); стили компонентов — CSS Modules рядом с ними (`TodoPage.module.css`, `TodoItem.module.css`, `TodoToolbar.module.css`); правила View Transition — `shared/withViewTransition.css`. Иконки задаются PascalCase-именами из набора `@gtk-js/icons-adwaita` (он приходит транзитивно с `@gtk-js/adwaita` и подключается `AdwaitaProvider`, напрямую не импортируется и в зависимостях проекта не указан) (`DocumentEdit`, `WeatherClear`).
- `public/` — статические файлы, доступные по URL от корня; сейчас там только `favicon.svg`.
- Unit-тесты запускаются через Vitest 5 в Node-окружении и используют общий `vite.config.ts`, включая алиас `@/`. Тесты лежат рядом с модулями: `todo/todoStore.test.ts`, `theme/theme.test.ts`.
- E2E-тесты находятся в `e2e/` и запускаются через Playwright в Chromium. Общие помощники лежат в `e2e/helpers.ts` (импортировать как `./helpers.js`): задачи ищутся по роли `listitem` и имени (`todoRow`, `todoRows`), статус меняют `markDone` (кнопка) и `swipeRow` (касания через CDP, с паузами: от мгновенного жеста Chromium запускает инерцию, и следующий тап не засчитывается как клик). `playwright.config.ts` автоматически поднимает Vite на `127.0.0.1:5173`; браузеры устанавливаются локально в `node_modules` через `PLAYWRIGHT_BROWSERS_PATH=0`, поэтому после `npm ci` нужно повторить `npm run test:e2e:install`.
- В `tsconfig.app.json` явно не включён `strict`; не описывать текущую конфигурацию как strict, пока это не изменено.

Нечётные версии (25, 27) и Node 20 (EOL) не поддерживаются. При выходе новой LTS-линии проверять зависимости и обновлять `engines` и `.nvmrc`.
- После изменений кода запускать как минимум `npm run build`, `npm run lint` и `npm run test:run`, а также `npm run fmt:check` для проверки форматирования.

- Деплой: `.github/workflows/deploy.yml` (GitHub Pages) запускается при push в `main` и вручную (`workflow_dispatch`); job `build` (Node из `.nvmrc`) выполняет `npm ci`, `lint`, `fmt:check`, `test:run` и `build`, job `deploy` публикует `dist`. Путь сайта передаётся через `BASE_PATH` (`base` в `vite.config.ts`, по умолчанию `/`); в настройках репозитория Pages → Source должен быть «GitHub Actions». E2E в workflow не входят. Версии actions закреплены по мажорным (`checkout@v7`, `setup-node@v7`, `configure-pages@v6`, `upload-pages-artifact@v5`, `deploy-pages@v5`) и должны работать на Node 24: Node 20 удалён с раннеров GitHub 23.09.2026 (https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/), actions на Node 20 падают. Перед обновлением проверять `runs.using` в `action.yml` нужного тега.
- `vite.config.ts` включает CSS sourcemaps только для dev-сервера через `css.devSourcemap`; исходный код в dev-режиме Vite сопровождается sourcemaps по умолчанию. Production sourcemaps отдельно не включены.

## Архитектура по мере роста

Структура плоская: `app/` собирает приложение, остальное — модули по предметной области (`todo/`, `theme/`) с моделью и UI рядом. Слои (`pages`, `features`, `entities`, `shared`) вводить только когда появляется реальная сложность: несколько маршрутов, переиспользование между модулями, сетевой слой.

```text
src/
  app/                 # провайдеры, шапка, глобальная композиция, router при появлении
  todo/                # store, действия и UI задач
  theme/               # тема приложения
  shared/              # нейтральные хуки и утилиты (useMediaQuery, useDeviceInfo); ui, api — по необходимости
```

- Направление зависимостей: модуль предметной области не импортирует другие модули и `app`; `app` их собирает; `shared` не знает о модулях, а модули могут импортировать `shared`.
- Не создавать пустые папки и файлы «на будущее». Для небольшого примера допустимо оставить код рядом с компонентом, а выделить модуль при повторном использовании или росте ответственности.
- Barrel-файлы `index.ts` добавлять, только когда модуль вырос и нужен явный публичный API; сейчас файлы импортируются напрямую (`@/todo/TodoPage`).
- Не помещать всё в `shared`: это слой действительно переиспользуемого и не зависящего от предметной области кода.
- Глобальные providers, router и композиция не должны попадать в бизнес-модели.
- Путь данных и состояния должен быть явным: UI вызывает действие, действие меняет состояние или обращается к API, компонент подписывается только на нужный результат.

## React и TypeScript

- Писать функциональные компоненты; `React` импортировать только если он действительно нужен. Соблюдать правила hooks и существующий `StrictMode`.
- Компонент должен иметь понятную ответственность. Разделять его по поведению или предметному смыслу, а не механически по числу строк.
- Состояние хранить максимально близко к месту использования. Локальное UI-состояние не переносить в Zustand без причины.
- Не дублировать производимые значения в state: вычислять их из исходных данных. Не синхронизировать props в state без необходимости.
- `useEffect` применять для синхронизации с внешними системами, а не для обычной цепочки вычислений или обработки пользовательского события.
- Не добавлять `useMemo` и `useCallback` без измеримой причины или необходимости стабильной ссылки. Сначала простой и понятный код.
- Использовать стабильные ключи списков, не индекс при изменяемом порядке или составе.
- Держать типы рядом с принадлежащим им модулем. Общие типы выносить только при реальном совместном использовании.
- Избегать `any`, небезопасных приведений и `@ts-ignore`; на внешних границах валидировать неизвестные данные и сужать `unknown`.
- Для импортов только типов использовать `import type`. Не подавлять ошибки TypeScript ради успешной сборки.
- Для абсолютных импортов из `src` использовать алиас `@/...`: `@/*` сопоставлен с `src/*` одновременно в `tsconfig.app.json` и `vite.config.ts`. При изменении алиаса обновлять обе конфигурации.
- Предпочитать именные экспорты для новых модулей, кроме мест, где default export является принятой точкой входа. Не менять существующие экспорты без необходимости.

## Zustand

- Текущий паттерн: hook `useTodoList` отвечает за подписку на состояние, команды экспортируются отдельно. Состояние и все действия над задачами лежат в одном `todo/todoStore.ts`.
- Подписываться через узкие селекторы: `useStore((state) => state.value)`. Не выбирать весь store и не создавать в селекторе новые объекты/массивы без стабилизации — это может вызывать лишние рендеры или зацикливание.
- Действия должны выражать предметную операцию, а не раскрывать компонентам детали устройства store.
- Обновления состояния делать иммутабельно. Не мутировать вложенные объекты из текущего состояния напрямую.
- Не хранить в глобальном store временное локальное состояние формы, открытие локального меню и другие данные одного компонента без потребности совместного доступа.
- Для async-операций явно моделировать loading/error/данные, обрабатывать ошибки и не оставлять устаревшие запросы способными перезаписать более новый результат.
- Не создавать отдельный store для каждого небольшого значения; граница store определяется связной областью состояния и сценариев.

## UI, стили и доступность

- Интерфейс строить из компонентов `@gtk-js/adwaita` (`Adw*`, `Gtk*`) и их style-классов (например `destructive-action`, `circular`); тему задавать централизованно через `AdwaitaProvider`. Собственные стили компонента — только в CSS Modules (`Component.module.css`) рядом с ним, без слоя (стили Adwaita не в слоях и перекрыли бы стили в слое), не в `index.css` и не inline, кроме значений, зависящих от данных (например `view-transition-name: todo-<id>`). В слой `reset` попадает только сброс браузерных значений, остальные глобальные стили — в слой `base`. Не добавлять собственный CSS без необходимости. Текст пользователя в `AdwActionRow` выводить с `useMarkup={false}` или экранировать.
- Не дублировать готовые возможности Adwaita собственными сложными контролами.
- Интерактивные элементы должны быть доступны с клавиатуры, иметь видимый focus и понятное accessible name. Использовать семантический HTML вместо кликабельных `div`.
- У кнопок внутри форм явно задавать `type`; изображениям давать осмысленный `alt`, декоративным — пустой `alt`.
- Учитывать responsive layout, переполнение длинным текстом, состояния hover/focus/disabled/loading/error и reduced motion там, где появляется анимация.
- Не полагаться только на цвет для передачи ошибки или статуса.

## Маршрутизация, API и производительность

- При добавлении страниц настройки router и providers держать в `app`, а реализацию страниц — в модулях предметной области или в `pages`, если страниц станет несколько.
- Для независимых крупных маршрутов рассматривать lazy loading, но не дробить мелкое приложение на множество chunks без пользы.
- Сетевую инфраструктуру отделять от UI: функции запросов, обработка ошибок и преобразование внешних данных не должны быть размазаны по JSX.
- Не хранить секреты во frontend-коде или `VITE_*` переменных: всё попадающее в клиентский bundle считается публичным.
- Избегать `dangerouslySetInnerHTML`; если без него нельзя обойтись, сначала обеспечить санитизацию и отдельно обосновать решение.
- Оптимизации делать после проверки реальной проблемы: сначала устранить лишние подписки, тяжёлые вычисления и большие зависимости, затем применять мемоизацию или разбиение кода.

## Проверки и изменения

- Сначала читать существующий код и сохранять пользовательские незакоммиченные изменения. Выполнять минимальный набор изменений для задачи.
- Не менять архитектуру, зависимости или конфигурацию попутно с небольшой задачей без необходимости.
- Не добавлять новые библиотеки, если задача просто решается текущим стеком или платформенными API.
- Тестировать поведение, а не детали реализации. Unit-тесты размещать рядом с проверяемым модулем с суффиксом `.test.ts` или `.test.tsx`; Zustand-store сбрасывать в `beforeEach`, чтобы тесты были изолированы. E2E-тесты размещать только в `e2e/` с суффиксом `.spec.ts`; использовать role-based locators и web-first assertions Playwright. Для будущих React UI-тестов добавить Testing Library и DOM-окружение отдельно, когда появится такая необходимость.
- После изменений проверять затронутый сценарий и сообщать, какие команды реально запускались. Если проверка не запускалась или падает, явно указывать это и причину.
- При изменении команд, структуры, стека или принятых соглашений обновлять этот файл. `README.md` использовать для пользовательской документации, а не дублировать здесь человекочитаемый guide без необходимости.
